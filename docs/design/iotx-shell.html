How permissions work

Every switch an admin sees comes from one rule: a person can do something only if their plan includes it, one of their roles grants it, nothing denies it, and (for a specific file or record) they have access to that item. Every app follows the same rule, from the builder to the ledger.

Five layers, checked in order

1 · PlanWhat the company bought
The organization's subscription sets the ceiling. A feature not in the plan shows as locked with "Upgrade" in the admin screen and can't be granted to anyone.
2 · App accessCan they open the app?
On or off per role. When it's off, the app disappears from the sidebar, the nine-dot launcher, search and AI answers.
3 · FeaturesWhat they can do inside it
One switch per feature: "Publish", "SQL editor", "Delete sales voucher", "Export sheet". Some features take a limit instead of on/off: an amount ceiling for vouchers, monthly AI credits, a date range for back-dated entries.
4 · Data scopeWhich data they can touch
Which companies or branches in the ledger, which departments' folders, which projects. "Only their own" is a scope too (a sales executive sees only their own customers).
5 · Item sharingThis file, this app, this board
Owner, editor, commenter or viewer on a single document, sheet, built app or task board, as in Google Docs. Sharing can never give more than the role allows: a viewer role can't be made editor of a sheet.

Roles

  • Built-in roles that can't be deleted: Owner, Admin, Member, Guest.
  • Role templates per industry, ready to copy and adjust: Accountant, Sales executive, Store keeper, Plant head, Dispatch clerk, Builder.
  • Custom roles made from scratch or copied from any role.
  • A person can hold several roles; their permissions add up. A deny on a person (for example "never delete vouchers") wins over every grant.
  • Per-person exceptions and temporary access ("give Anita the SQL editor until Friday") expire on their own.
  • Roles can be assigned to departments and groups, including groups from the company's sign-in system (SSO and SCIM, which the builder already supports).

How each app declares its features

Each app ships a small permission list, its manifest. The admin screen builds its switches from it automatically, so a new feature in any app shows up as a new switch without changing the admin screen.

{
  "app": "ledger",
  "name": "Ledger",
  "features": [
    { "key": "ledger.voucher.sales.create",  "label": "Create sales vouchers",  "group": "Vouchers", "default": ["Accountant"] },
    { "key": "ledger.voucher.sales.delete",  "label": "Delete sales vouchers",  "group": "Vouchers", "risk": "high" },
    { "key": "ledger.voucher.amount_limit",  "label": "Largest voucher amount", "type": "limit", "unit": "INR" },
    { "key": "ledger.backdate.days",         "label": "Back-dated entries",     "type": "limit", "unit": "days" },
    { "key": "ledger.reports.balance_sheet", "label": "Balance sheet",          "group": "Reports" }
  ],
  "scopes": [ { "key": "company", "label": "Companies" }, { "key": "branch", "label": "Branches" } ]
}

Where the checks happen

  • The screen hides what you can't use. Buttons, menu items and apps a person can't use aren't shown. Where hiding would confuse, they show greyed out with "Ask your admin".
  • The server refuses it anyway. Every app's server checks the same permission before acting, so a hidden button can't be worked around.
  • One sign-in, one permission service. When someone signs in, the platform gives each app a short-lived pass listing their roles. Apps ask the platform's permission service when they need a decision, and cache the answer for a few seconds.
  • Everything is logged. Who changed which switch, who was refused what, and when. Admins can "Preview as" any role before saving.

How to build the IOTx ecosystem

Today there are separate apps: the Builder (web/), Sheets (apps/sheets), the Tally-style Ledger (apps/tally), Books (zoho-books), and the Docs and Slides engines (suite/wordcraft, suite/deckcraft). The plan is to put one platform underneath all of them and one shell around them, so they feel like a single product.

The three parts

Part 1

IOTx Platform

One place for accounts and sign-in, organizations and departments, roles and permissions, the app list, billing and plans, the audit log, notifications, search and the AI. Every app uses it; none keeps its own users.

Part 2

IOTx Shell

What you see in the prototype: the sidebar, top bar, nine-dot launcher, theme, search and notifications. Every app sits inside it, so moving from Sheets to the Ledger feels like one product.

Part 3

The apps

Builder, Sheets, Docs, Slides, Ledger, Books, Tasks, Files, Notes, Chat, Mail, Calendar, Meetings, Read and Store. Each keeps its own engine and declares its features in a permission manifest.

Decisions I recommend

Where the platform livesGrow it out of the Builder (web/)It already has users, workspaces, organizations, roles, SSO, SCIM, API keys, audit logs and billing, all tested.
Sign-in across appsThe platform signs everyone in; apps receive a short-lived pass (OIDC/JWT)One login for every app. The Builder already speaks OIDC.
Addressesiotx.app for the shell, app.iotx.app/sheets, /ledger… under one domainOne session cookie, no cross-site sign-in problems, simple for clients.
Shared lookOne design system package (colours, type, components, icons) used by every appEach app is built separately today; a shared package makes them match.
Permission storagePlatform database: roles, grants, denies, scopes, item sharesOne source of truth; apps never keep their own role tables.
DataEach app keeps its own database; the organization ID is on every recordApps stay independent and can scale on their own; one organization never sees another's data.

Build order

Step 1

Design system and shell

  • Lock colours, type, icons, spacing and components from this prototype, in light and dark with four accents.
  • Build the shell: sidebar, top bar, launcher, theme, search, notifications, account menu, phone layout.
Step 2

Platform: identity and permissions

  • Organizations, departments, people, roles, role templates, custom roles, denies, temporary access.
  • The permission service, the manifest format and the auto-generated admin screen with "Preview as".
  • Sign-in pass for apps; audit log for every change.
Step 3

Home and the Builder

  • The home page in the prototype becomes the real landing page after login.
  • Map every Builder feature to a switch (the list in the Permission model tab) and enforce them.
Step 4

Sheets joins

  • Add accounts and permissions (its README says it has none yet): open, edit, share, export, AI, scripts.
  • Sheets as a data source for built apps.
Step 5

Ledger and Books join

  • Sign-in through the platform; companies and branches as data scopes.
  • Voucher-level switches (create, alter, delete, approve per voucher type), amount limits, back-dating limits, period locks, report access.
Step 6

Docs, Slides, Tasks, Files, Notes

  • Web apps on the wordcraft and deckcraft engines; Tasks with boards and sprints; Files with department folders.
Step 7

Chat, Mail, Calendar, Meetings, Read, Store

  • Connect Google or Microsoft mail and calendar first; IOTx's own later.
  • Store with company apps and IOTx templates; "Add new" for outside apps.
